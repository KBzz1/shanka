## 1. 产品定位与本期问题

### 1.1 产品定位

面向所有需要长期记忆知识的用户，帮助用户把具有文本层和目录结构的 PDF 转化为闪卡，并通过每日学习、
到期复习和进度反馈持续巩固记忆。

### 1.2 V2.5 要解决的问题

当前产品已经存在部分页面和后端能力，但仍处于 Debug/演示与正式产品并存的状态：部分按钮不可用，
部分页面使用硬编码或 Mock 数据，制卡被中断后需要重复上传和配置，生成卡片后缺少连贯的学习计划、
复习和统计闭环。V2.5 的目标不是继续堆叠入口，而是把核心链路打磨到普通用户可持续使用的程度。

### 1.3 优先级

V2.5 按以下顺序处理产品质量：

1. 错误与恢复体验；
2. 核心流程衔接；
3. 性能与稳定性；
4. 页面和交互完整性；
5. 学习与复习效果；
6. 真实数据展示；
7. AI 制卡质量。

## 2. 产品原则

- **以学习项目为中心**：PDF、章节、牌组和历次制卡任务组成一个可持续学习的项目。
- **自动保存，不让用户重做**：上传成功后持续保存步骤和配置；退出 App、切换页面或更换设备后可继续。
- **先恢复，再重来**：可恢复错误提供明确重试入口；失败结果不得伪装成部分成功。
- **真实数据优先**：Release 不展示内置演示牌组、固定统计、伪成功或未实现占位页。
- **学习闭环优先**：制卡完成后必须能进入学习计划、评级复习和统计，不把“生成成功”当作产品终点。
- **语义控制覆盖范围**：精简、均衡、充分覆盖表达知识覆盖深度，不向用户承诺固定卡片数量。
- **算法归服务端**：用户只做“忘记／困难／良好／简单”自评，不理解或手动调整排程算法。
- **产品与实现证据分离**：PRD、设计、代码、测试、APK 和真实设备验收是不同完成层级。

## 3. 核心术语与归属

| 术语 | 定义 |
| --- | --- |
| 学习项目 | 围绕一份 PDF 建立的长期学习容器，包含 PDF、章节、项目内牌组、制卡任务历史及学习范围。 |
| 当前学习项目 | 用户当前每日学习与到期复习所针对的唯一项目；同一时刻只能有一个。 |
| 制卡任务 | 在一个学习项目中，基于一次章节选择和生成配置执行的制卡过程。一个项目可有多次任务。 |
| 失败重试任务 | 从失败任务复制已确认配置后创建的新制卡任务；原失败任务保留，并显示两者关联。 |
| 牌组 | 卡片集合。PDF 生成牌组默认归属于创建它的学习项目，不跨项目追加。 |
| 新卡 | 从未提交过任何一次有效评级的卡片。 |
| 已学习卡 | 至少提交过一次有效评级的卡片。 |
| 到期卡 | 根据服务端 FSRS 排程，当前时间已经到期的已学习卡。 |
| 自由刷题 | 只浏览卡片，不记录评级，不改变学习进度或复习计划。 |
| 单卡 AI 重写 | 用户侧名称为“AI 重新生成”：基于原 PDF 来源为一张正式卡生成预览，确认后安全替换。 |
| 学习时区 | 账号级 IANA 时区，用于确定“今天”、自然周和连续学习天数；所有设备使用同一值。 |

## 4. V2.5 端到端用户旅程

1. 用户以邮箱和密码登录；登录成功后进入真实首页。
2. 用户创建学习项目并上传 PDF；上传成功即自动保存项目。
3. 系统解析目录，用户确认或修订章节并选择本次制卡范围。
4. 用户选择覆盖深度、三档难度比例和自定义要求，生成样卡。
5. 用户确认样卡并开始正式制卡；任务在后台继续，离开页面或设备不影响进度。
6. 任务成功后一次性显示全部卡片并进入项目牌组；失败时不显示部分结果，可直接重试。
7. 用户把一个学习项目设为当前项目，圈定新卡章节范围和每日学习量。
8. 首页“今日目标”优先安排当前项目的到期卡，再以范围内新卡补足计划。
9. 新卡学习和到期复习都在显示答案后选择“忘记／困难／良好／简单”。
10. 评级结果更新后续排程、项目进度和统计页真实数据。

## 6. 本期不包含

- OCR、扫描版或纯图片 PDF；
- 邮箱找回密码、修改登录邮箱、OAuth、第三方登录、多因素认证；
- 游客模式、匿名账号或旧匿名数据认领；
- 多设备离线编辑冲突的人工合并界面；
- AI 自动修复、自动淘汰、自动补卡、自动重平衡或按固定数量补齐；
- 用户侧成本预估、Token 消耗、跳过明细或模型内部评分展示；
- 自定义头像上传、拍照、裁剪或外部头像 URL；
- 卡片回收站；
- 制卡任务暂停；
- 管理后台、运营平台或多实例基础设施改造；
- iOS、桌面端或网页端正式发布。

## 7. 跨模块业务规则

### 7.1 数据同步

除主题等明确声明为本机偏好的设置外，用户资料、学习项目、PDF、章节、制卡任务、牌组、卡片、
学习范围、每日学习量、学习时区、难度默认值、复习状态和统计数据均归属于登录账号并跨设备可见。

### 7.2 错误与恢复

- 网络失败、会话失效、PDF 解析失败、生成失败和保存失败必须使用可区分的真实状态；
- 可重试错误保留用户已经完成的输入和配置，不要求重新上传 PDF；
- 失败不得显示成功图标、完成文案、虚构卡片或固定统计；
- 会话失效时引导重新登录；重新登录后仍能回到原学习项目和制卡任务；
- 长时间操作允许用户离开页面，返回后读取服务端最新状态。

### 7.3 删除保护

- 单张卡片删除采用 10 秒“撤销”提示，V2.5 不提供回收站；
- 删除章节、牌组或学习项目前必须二次确认并说明影响范围；章节仍遵循活跃任务保护，牌组和项目确认删除后由服务端
  自动取消关联活跃任务并使迟到的 worker 写入失效，不向用户暴露任务处理选项；
- 删除制卡任务时，默认保留已经生成的卡片，用户可主动选择连同该任务生成的卡片一起删除。
- 解析中的学习项目可以直接删除；服务端让解析租约失效并丢弃迟到结果。正式生成中的任务在项目或牌组删除时一并
  自动取消，正式生成前的任务也不再要求用户先单独放弃。

### 7.4 Release 真实性

Release 中所有可见入口必须满足以下之一：真实可用，或不展示。不得以“未构建”、空白占位页、
Debug Toast、固定成功结果或无效按钮替代真实能力。

## 8. 模块完成定义

除非某条需求明确标记为 P1 或“本期不包含”，V2.5 总 PRD和所有模块 PRD中的 FR、AC 及跨模块主链路
默认均为 **P0 发布要求**。文档不得再使用未定义的“P0 模块”概念；模块只有“全部 P0 通过”或“未通过”。

一个模块只有同时满足以下条件才可标记为“V2.5 模块验收通过”：

1. 模块 PRD 中所有 P0 功能需求和验收标准有真实实现；
2. 页面状态覆盖加载、成功、空数据、可恢复失败和不可恢复失败；
3. 不依赖 Mock、内置演示数据或伪成功提示；
4. 账号隔离、跨设备读取、重复提交和中断恢复按模块适用范围通过；
5. 对应契约、实现和验证证据可追溯，但不得用文档或测试名称代替真实结果。

V2.5 正式发布还必须通过 [Release 与跨模块验收](release-and-acceptance.md) 中的 APK 和完整主链路验收。
